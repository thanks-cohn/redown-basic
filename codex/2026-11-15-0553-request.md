## Primary directive

Build **REDOWN Basic** as an independent, dependable fallback product. This is **not REDOWN 2.0**. It must not carry REDOWN's UI, architectural, experimental, or operational baggage.

**The entire product:**
1. Google Drive, Dropbox, and OneDrive.
2. Exactly three direct, **flat native Chrome right-click menu** actions: **Save to Google Drive**, **Save to Dropbox**, **Save to OneDrive**.
3. A compact, restrained, cohesive **Shelf with exactly three provider cards**.
4. The **minimum** OAuth, token refresh, permission/readiness checking, source-byte acquisition, upload, provider-side confirmation, and failure handling required for those saves.

**Everything else is out of scope.** Do not implement speculative features, new destinations, custom hierarchy, dashboards, full explorers, extras, or broad infrastructure. Favor proven code extraction and *smaller* dependencies over wholesale copying.

## 2. Native menu: exactly three flat actions

Register the following direct Chrome context-menu items, with no nested menus:

- Save to Google Drive
- Save to Dropbox
- Save to OneDrive

A user right-clicks a supported image, file link, or downloadable web resource, selects a provider, and a save attempt begins. Preserve genuinely working source handling, filename/extension preservation, and appropriate upload strategies.

Do not introduce Simple/Narrow/Depth, folder trees, custom destinations, extra menus, custom nested popouts, or providers beyond the three listed.

Unsupported, protected, non-downloadable, blocked, or HTML/login-page resources must report a truthful failure. A right-click alone must **never** count as successful uploading.

**Privacy requirement:** Send the receiving provider the file bytes, filename/extension, and only technical metadata its upload API requires. Do **not** transmit source/page URLs or unrelated browsing information to providers.

## 3. Small, standardized Shelf: three cards and nothing more

Use a small, visually coherent Shelf with **one card per provider**, in consistent order:

**Google Drive | Dropbox | OneDrive**

Every card uses the **same layout, sizing, typography, spacing, borders, buttons, and status vocabulary**. A restrained, professional style is required; do not assemble three different old designs.

Only essential controls/state:
- Provider name and recognizable icon
- Connection/readiness indication
- **Sign In** or **Reconnect** when required
- **Refresh** status, distinct from signing in
- Concise latest save outcome or required action

Status must accurately distinguish: **Not connected**, **Connected but not ready**, **Ready**, **Reauthorization required**, **Temporary failure**. Refresh should not repeatedly invoke interactive OAuth when credentials can be reused or renewed silently. Logged-in status does **not** equal permission to save.

A minimal per-save status or notification is allowed for success/failure. No dedicated history, elaborate saved-items gallery, analytics, counters, audio, animation, or visible queue dashboard.

## 4. Right-click save reliability

**Google Drive**
- Reuse actual functioning OAuth and upload mechanics.
- Distinguish real bytes from HTML, authentication pages, and error responses.
- Preserve filenames and extensions where possible.

**Dropbox**
- Reuse functioning OAuth and session/chunked-upload mechanics where appropriate.
- Never confuse queued/uploading with provider-confirmed success.
- Handle expiration and interrupted upload correctly.

**OneDrive**
- Reuse functioning Microsoft OAuth and upload-session mechanics.
- Address known/unknown source length through a supported, correct strategy; report a real limitation when unavoidable instead of pretending success.
- Require a provider-confirmed uploaded item before reporting success.

**All three**
- Check actual *save readiness*: valid credentials, appropriate scopes, and operational permissions.
- Refresh credentials silently when possible; use narrowly targeted reauthorization when needed.
- Preserve the intended pending save across reauthorization **only** if secure and safely resumable, without accidental duplicate objects.
- Obtain actual file bytes through an appropriate source-access path; do not upload a website's HTML error page as a file.
- Retain reliable filename/extension and content-type handling.
- Support reasonable file sizes through provider-appropriate transfer strategies; do not promise unlimited sizes without proof.
- Handle failures, retries, service-worker restarts, and missing permissions truthfully.
- Avoid browser-disk staging where safe direct byte transfer is available.
- Treat provider confirmation (and independent verification where feasible) as the success boundary, not a timer, menu click, animation, queue entry, or HTTP request initiation.
- Show a concise useful error rather than a success claim for blocked resources, unknown lengths, expired scopes, network failures, and provider rejects.

**Explicitly reject false success.** Preserve only essential internal transfer state and minimal diagnostics needed for reliability; keep them unobtrusive.

## 6. Independence and OAuth isolation

REDOWN Basic must be installable as its **own unpacked Chrome extension**, with:
- Its own manifest and background service worker
- Its own OAuth client/redirect configuration appropriate to its Chrome extension ID
- Its own local storage namespace and clean-install behavior
- Its own three-card Shelf
- Its own minimal build/test procedure

Never assume OAuth clients, identity redirect URIs, existing REDOWN login state, cached tokens, live Workers, or external services will transfer across extension identities. Document user-provided configuration and any permissions/consent required. **Never copy credentials or secrets.**

No runtime imports or dependencies from REDOWN or Click2Cloud, and no shared running service as a prerequisite.
